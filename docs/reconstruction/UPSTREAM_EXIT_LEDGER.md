# TAVERN EXIT LEDGER
## Source-Independent Reconstruction / Reverse-Engineering Authority

**Status:** Draft reconstruction authority  
**Purpose:** Allow a future implementation team to replace every Tavern-derived component without needing to reopen Tavern source or documentation.  
**Scope:** Retired WoW Classic client authentication/account/BGS compatibility only, plus the missing platform layers required by our larger product.

---

# 0. Non-negotiable objective

We may use Tavern-derived code as an interim subsystem.

The long-term objective is different:

> For every Tavern-derived component, produce enough source-independent behavioral authority that a future engineer can close the Tavern repository, never look at it again, and still know what must be implemented, how to discover unknowns, and how to prove compatibility.

This ledger is therefore **not a list of files to rewrite**.

It is a **reconstruction specification**.

A valid replacement must be derived from:

1. public protocol standards,
2. black-box observations of retired client behavior,
3. packet captures generated independently,
4. protocol definitions recovered independently from client binaries where lawful,
5. interoperability testing against retired clients,
6. independently licensed/reference implementations used only as permitted,
7. this ledger's behavioral contracts.

A replacement must **not** be produced by line-by-line translation, variable renaming, porting, or paraphrasing of Tavern source.

---

# 1. Clean-room operating rule

Once a subsystem enters replacement work:

## Research lane may inspect
- retired client binaries
- traffic generated by those clients
- public standards
- public protocol documentation
- packet parsers
- independently licensed references
- behavior of the running compatibility service as a black box
- this ledger

## Implementation lane receives
- protocol contracts
- state diagrams
- field tables
- test vectors
- captured request/response fixtures produced independently
- expected error behavior
- acceptance tests

## Implementation lane must not receive
- Tavern source
- Tavern comments
- Tavern test source
- Tavern internal helper design
- copied SQL migrations
- copied HTML/CSS/JS
- copied internal naming unless the name is required for interoperability
- copied function decomposition
- copied control flow

## Replacement status vocabulary

- `TAVERN-DERIVED` — copied or modified Tavern implementation remains.
- `BEHAVIOR-IDENTIFIED` — external responsibilities are known.
- `CAPTURE-REQUIRED` — behavior exists but must be independently observed.
- `SPEC-READY` — independent implementation specification is complete.
- `IMPLEMENTED-INDEPENDENTLY` — implementation lane completed its own code.
- `INTEROP-VERIFIED` — real supported clients pass.
- `TAVERN-FREE` — no Tavern-derived implementation remains in this component.
- `UNKNOWN` — insufficient evidence.
- `CONFLICT` — current sources disagree and cannot yet be treated as authority.

A component is not considered clean-room replaced until it reaches:

`SPEC-READY -> IMPLEMENTED-INDEPENDENTLY -> INTEROP-VERIFIED -> TAVERN-FREE`

# 2. Evidence hierarchy

Use this order when facts conflict:

1. **Real retired client behavior reproduced by us**
2. **Packet captures produced by us**
3. **Repeatable black-box tests**
4. **Protocol data recovered independently from the target client**
5. **Published standards**
6. **Independent third-party implementation behavior**
7. **Tavern documentation as a research lead only**
8. **Tavern source behavior as temporary black-box oracle only**
9. **Assumption**

Tavern documentation is not final authority.

Known example: Tavern's main plan reports broad BGS completion while its BGS-version document still describes v2 work as planned/research. This must be treated as `CONFLICT` until independently verified.

# 6. Credential and SRP reconstruction dossier

## Target behavior

Modern Battle.net-style web/game login uses an SRP-family proof rather than sending a reusable password verifier over the wire for the later Classic client lines.

The exact variant cannot be implemented from generic RFC SRP assumptions alone.

## Independent reconstruction tasks

For every supported client family:

1. capture challenge response,
2. record negotiated:
   - modulus size,
   - generator,
   - hash algorithm,
   - iteration count,
   - salt width,
   - username normalization,
   - public ephemeral encoding,
3. determine integer byte order,
4. determine hash-input byte order,
5. determine KDF,
6. determine proof construction,
7. determine server proof,
8. determine credential storage format,
9. determine password-change migration behavior.

## Required test vectors

Create our own vectors:

```text
login
password
salt
client_private_a
client_public_A
server_private_b
server_public_B
scrambling_parameter_u
derived_x
verifier_v
session_secret_S
session_key_K
client_proof_M1
server_proof_M2
```

At least:
- one ASCII credential,
- one mixed-case credential,
- one Unicode account name if accepted,
- wrong password,
- wrong salt,
- malformed A,
- replayed proof.

## Do not assume

- RFC 5054's exact encoding,
- legacy WoW realm SRP behavior,
- the same SRP variant across all client generations.

## Completion gate

Independent SRP code must:
- reproduce our test vectors,
- authenticate against every supported retired client family,
- reject altered proofs,
- never require Tavern crypto code.

# 33. AGPL exit rule

Adding our own code around a Tavern-derived component does not make that component cease to be Tavern-derived.

The exit path is component replacement:

```text
TAVERN-DERIVED COMPONENT
        ↓
external behavior documented
        ↓
independent evidence collected
        ↓
source-independent specification frozen
        ↓
separate implementation written
        ↓
black-box compatibility verified
        ↓
old component removed
        ↓
TAVERN-FREE
```

Do not call a component Tavern-free because:
- it was renamed,
- it was moved into another process,
- most lines changed,
- it was translated to another language,
- function names changed,
- comments were removed.

The replacement must actually be independently implemented.

---

# 34. Definition of "no recourse"

A reconstruction package is adequate only when a new engineer can receive:

- this ledger,
- our independent protocol specs,
- our capture corpus,
- our black-box test harness,
- our test vectors,
- supported retired clients,
- public standards,

and can complete the replacement **without asking for Tavern source or docs**.

If the engineer says:

> "I need to look at how Tavern did this"

then the reconstruction package is incomplete.

That missing fact becomes a new `CAPTURE-REQUIRED` item.
